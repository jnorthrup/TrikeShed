# Offline and development operating procedures

## Preparing a demonstration

Select the frozen integrated build and a fixture bundle. Verify every required artifact and executable against its manifest. Start from a new run namespace so old assumptions, reviews or productions cannot satisfy the demonstration accidentally. Record the hardware, heap/worker configuration and deployment profile.

Confirm source availability, derivative lineage, parser/solver readiness, local browser assets and storage headroom. Optional models may be absent. Show those absences in the wizard rather than substituting a remote provider. Verify the current effect policy allows only the intended local fixture effects.

Run a short egress probe for host and worker paths under the selected profile, then execute one source-to-result smoke scenario. Preserve its receipt. A failed readiness check blocks the affected lane and leaves the rest of the graph inspectable.

## Running and observing

Admit work with a retained definition, frame and budget. Monitor queue age, active tasks, result retention, source coverage and projection lag. Use the inspector to distinguish execution failure, semantic uncertainty and missing authority. A low activity rate may be correct when no inputs are eligible.

When the UI becomes busy, adjust aggregation or presentation pace. Use execution throttling only through an explicit host command. If a source changes, create a new frame; do not repair displayed quotations in place while keeping old proof identity.

## Pausing and changing the scaffold

Request a scope or whole-run hold. Wait for the recorded boundary acknowledgement and inspect outstanding effects. Save a checkpoint. Edit a copy of the graph, review the affected/reused artifact list and validate budgets. Resume as a new epoch for semantic changes; use a view-only version for layout changes.

If an engine cannot stop internally, choose its declared process termination/restart path and retain the incomplete attempt. Never interpret a stopped animation as a stopped worker. If the browser disappears, reconnect by run ID and recover control sequence from the host.

## Production maintenance

Inspect shadow disagreements and net saved work before admission. Active generations expose dependency currentness, last validation, match counts, effect receipts and fallback. Withdraw or expire a generation through the owner; do not delete its historical record.

When a source/review changes, suspend affected generations before admitting new effects. Reconcile already dispatched effects. Recompute or revalidate through a new candidate/generation. A broad conservative suspension is acceptable when dependency coverage is incomplete; label its breadth and cost.

## Incident procedure

1. Retain the current journal watermark, run definition and failure receipt.
2. Stop new admissions to the affected scope while preserving ownership of existing work.
3. Reconcile worker/process and effect state; mark uncertain outcomes explicitly.
4. Recover from the last valid snapshot and journal tail, verifying referenced artifacts.
5. Re-admit only eligible idempotent work under a new attempt identity.
6. Record cause, affected results and the regression/operational check that prevents recurrence.

Do not erase a failing run to obtain a clean demo. Keep a known-good fixture/build for an explicitly labeled replay while the failure is investigated.

## Retention and export

Retain sources required by current reviews, selected histories and active production dependencies. Diagnostic traces can have shorter retention than semantic receipts. Before garbage collection, calculate reachable roots and verify that retained proof/production records remain resolvable. A missing source downgrades availability and may suspend current use.

Export a self-contained run packet with definition, frame, selected journal, source manifests, proof/result references, policies and required local assets. If private bytes are omitted, include an explicit incomplete-export manifest. Hashes do not make an export independently replayable when payloads are absent.

## Unattended implementation campaign

The coordinator maintains a ready-work queue from the 25 packages, per-task budgets and ownership. Every worker starts from a frozen contract version and ends with a concrete handoff packet. Failed attempts consume budget and retain evidence. Repeated failure without new information stops that task and releases the lane to independent work.

Integrate frequently through the endorsed D3M method in [PRELOAD](../../../PRELOAD.md). Commit and publish distributed work before the local fetch/integration pass. Preserve base and both sides of conflicts, review intent across the complete set, verify composed behaviour and push master without force. The cloud document checkpoint and Jim's local all-branch integration are separate operations with separate evidence.

## Daily control review

Review accepted work, blocked dependencies, token/cache costs, machine spend, integration failures and semantic regressions. Compare actual throughput to the timeline assumptions. Reduce concurrency if contracts or integration cannot absorb work. Increase it only when ready tasks have independent ownership and the verifier is keeping pace.

## Release packet

A release includes a clean offline installation record, actual demonstration recording, semantic journal, benchmark/capacity report, recovery evidence, source/license manifest and limitations by delivery level. The reader must be able to identify which results are live measured execution, historical reports, synthetic load and proposals. No screenshot alone establishes provenance, isolation or production correctness.
